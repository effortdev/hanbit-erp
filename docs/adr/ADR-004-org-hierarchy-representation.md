# ADR-004: 조직 계층 표현 방식

- 상태: 승인됨
- 범위: Module 1 (조직/사원관리)

## 상황

㈜한빛전자의 조직은 "본부(3) - 팀(8)"의 **2단계 고정 깊이** 구조다(요구사항 문서의 조직도 참고). FR-1-1은 이 계층을 등록/조회할 수 있어야 한다고만 요구하고, 임의 깊이의 트리(예: 팀 아래 파트, 파트 아래 셀)를 지원하라는 요구는 없다. 조직 계층을 어떤 자료구조/스키마로 표현할지 결정해야 한다.

## 후보

1. **인접 리스트(Adjacency List, 자기참조 FK)** *(채택)* — `org_unit(id, parent_id)` 하나의 테이블로 본부/팀을 모두 표현. 구현이 단순하고 2단계 깊이에서는 조회 쿼리도 단순하다.
   ```sql
   SELECT id, name, type, parent_id FROM org_unit ORDER BY COALESCE(parent_id, id), type ASC, id;
   ```
2. **Materialized Path** — `org_unit(path VARCHAR)`에 `/1/3/` 같은 경로를 저장. 임의 깊이 조회가 문자열 LIKE 검색으로 가능해지지만, 이동(발령이 아니라 조직개편) 시 하위 경로를 일괄 갱신해야 하는 복잡도가 추가된다.
3. **Closure Table** — 모든 조상-자손 관계를 별도 테이블에 전개해 저장. 임의 깊이·복잡한 트리 질의에 강하지만, 본부-팀 2단계 구조에는 테이블과 유지보수 비용이 과하다.

## 결정

인접 리스트(1번)를 채택한다. `org_unit` 테이블 하나에 `type(HQ|TEAM)`과 `parent_id`(팀이면 소속 본부, 본부면 NULL)만 둔다.

## 근거

- 요구사항이 명시한 깊이는 2단계로 고정되어 있고, 가변 깊이 트리를 지원해야 한다는 FR/NFR이 없다. Materialized Path나 Closure Table은 "지원하지 않는 요구사항"을 위한 선제적 일반화이며, 이는 YAGNI 원칙에 반한다.
- 인접 리스트는 조회 쿼리(`selectOrgTree`)를 한 번의 `ORDER BY`로 정렬해 애플리케이션(JSP)에서 `parent_id` 기준으로 그룹핑하면 트리를 그릴 수 있어, 2단계 한정으로는 재귀 CTE조차 필요 없다.
- 향후 조직 개편으로 깊이가 늘어난다면 그 시점에 Materialized Path/Closure Table로의 마이그레이션을 별도 ADR로 재논의하면 된다 — 지금 미리 설계를 무겁게 가져갈 이유가 없다.

## 트레이드오프

- 이 스키마는 "본부-팀 2단계 고정"이라는 암묵적 전제에 의존한다. 만약 향후 3단계 이상 조직(예: 팀 아래 파트)이 필요해지면 조회 쿼리와 JSP 트리 렌더링 로직을 재귀 구조로 다시 짜야 한다.
- 인접 리스트는 "특정 본부 산하 전체 팀 목록"처럼 단순 질의는 쉽지만, 일반적인 임의 깊이 조상/자손 질의는 이 구조로 표현하기 어렵다. 지금 요구사항 범위에서는 발생하지 않는다.
