# ADR-009: 연차 잔여현황 계산 방식

- 상태: 승인됨
- 범위: Module 3 (근태관리)

## 상황

FR-3-3: 사원별 연차 잔여일수를 조회할 수 있어야 한다. 연차 부여 방식(입사일 기준 vs 회계연도 기준)과, 상신 중인 휴가가 잔여일수 계산에 어떻게 반영되어야 하는지를 정해야 한다.

## 후보 (부여 방식)

1. **입사일 비례(anniversary) 방식** — 입사일 기준 1년 단위로 갱신. 실제感과 가깝지만, 회계연도 전환·비례 계산(예: 연중 입사자의 첫 해 일수 계산) 로직이 복잡해지고, 이번 포트폴리오 범위에서 실제로 검증할 만한 사용 빈도가 낮은 엣지케이스다.
2. **회계연도(매년 1/1) 일괄 부여 방식** *(채택)* — 매년 1월 1일 기준으로 그 해의 근속연수를 계산해 그 해 전체 부여일수를 확정한다.

## 결정

회계연도 일괄 부여 방식을 채택한다. 근속연수에 따른 부여일수는 `vacation_policy` 테이블로 분리한다(코드에 규칙을 하드코딩하지 않음).

```sql
CREATE TABLE vacation_policy (
    min_years INT NOT NULL,
    max_years INT NULL,   -- NULL = 상한 없음(그 이상 전부 해당, 상한 25일 구간)
    annual_days INT NOT NULL
);
-- 1년 미만 11일, 이후 매년 +1일, 상한 25일
-- (0,0,11) (1,1,12) (2,2,13) ... (13,13,24) (14,NULL,25)
```

```java
int yearsOfService = Math.max(0, Period.between(employee.getHireDate(), LocalDate.of(referenceYear, 1, 1)).getYears());
int annualDays = vacationPolicyMapper.selectAnnualDays(yearsOfService); // 못 찾으면 BusinessException
```

연중 입사자(참조 시점인 1/1 이후에 입사)는 `Math.max(0, ...)`로 근속연수를 0년으로 바닥 처리해 "1년 미만 11일" 구간을 그대로 적용한다 — 월할 비례 계산은 하지 않지만(후보 1을 배제한 이유와 동일), 그렇다고 입사 첫 해에 연차를 0일 주는 것도 비상식적이라 최소 구간(11일)은 적용되도록 했다. 이 처리는 코드 주석으로 남긴다.

### 잔여 연차 계산: 상신 중 임시 차감 포함

```
잔여 연차 = 부여일수(annual_days)
          - 승인 완료(APPROVED) 휴가신청의 사용일수 합
          - 상신 중(PENDING) 휴가신청의 사용일수 합
```

```sql
SELECT COALESCE(SUM(days), 0) FROM attendance_vacation_request
WHERE employee_id = #{employeeId} AND status = #{status} AND YEAR(start_date) = #{year}
```

`days`는 신청 시점에 계산해 저장해두는 평일 기준 일수 스냅샷이다(휴일 캘린더 도입 등으로 계산 규칙이 바뀌어도 과거 신청 건의 값이 흔들리지 않도록). `PENDING`도 차감에 포함시켜, 승인 대기 중인 신청이 여러 건 겹쳐 잔여일수보다 많은 휴가가 동시에 걸려 있는 상황(승인되면 초과 사용이 되는 상황)을 상신 시점에 미리 막는다.

반려되면 상태가 `PENDING → REJECTED`로 바뀌고(Module 2의 이벤트 반영, ADR-008), 위 합계 쿼리가 `status = PENDING`만 세므로 반려된 건은 자동으로 계산에서 빠진다 — 별도의 "임시 차감분 롤백" 로직이 필요 없다. Module 1의 `emp_history`, Module 2의 `approval_step`/`approval_action`과 같은 맥락으로, 상태를 별도 잔액 컬럼에 미러링하지 않고 원천 테이블에서 매번 파생시킨다.

## 근거

- 회계연도 일괄 부여는 계산이 단순하고, 매년 1회(1/1) 갱신되는 실제 인사팀 운영 방식과도 크게 다르지 않다.
- `vacation_policy`를 테이블로 분리해 "1년 미만 11일, 매년 +1일, 상한 25일"이라는 규칙이 바뀌어도 코드 배포 없이 데이터만 바꾸면 되게 했다.
- 승인 대기 중 신청을 잔여일수에서 먼저 차감하는 것은, Module 2에서 리더 공석을 조용히 넘어가지 않고 예외로 막았던 것과 같은 원칙이다 — "나중에 문제가 될 수 있는 상태를 조용히 허용하기보다, 발생 시점에 안전하게 막는다."
- 잔액을 별도 컬럼으로 관리하지 않고 원천 테이블에서 파생시키는 것은, Module 1/2에서 이미 검증된 패턴(append-only 로그 + 파생 계산)을 그대로 재사용한 것이다.

## 트레이드오프

- 연중 입사자를 "근속연수 0년"으로 처리해 최소 구간(11일)을 그대로 주는 것은 실제 노동법상 월할 비례 부여보다 후하거나 박할 수 있다(예: 12월 입사자도 11일을 다 받음). 포트폴리오 범위에서는 문제 삼지 않지만, 실제 서비스라면 별도 검토가 필요하다.
- `YEAR(start_date) = 연도`로 연도를 구분하므로, 연말-연초에 걸치는 휴가 신청은 시작일 기준 연도로만 집계된다(예: 12/30~1/2 신청은 전부 작년 연차에서 차감). 신청 시 연도를 넘기지 않도록 안내하는 것으로 충분하다고 보고 별도 분할 로직은 두지 않았다.
- `PENDING` 차감 때문에, 사원이 여러 건을 동시에 상신했다가 전부 반려되면 그 사이 잔여일수 조회 화면이 일시적으로 낮게 보일 수 있다(반려 처리 전까지). 실제 잔여일수를 부정확하게 보고하는 게 아니라 "지금 확정되지 않은 위험을 미리 반영한 보수적인 값"이라는 점을 화면에서 설명할 필요가 있다.
